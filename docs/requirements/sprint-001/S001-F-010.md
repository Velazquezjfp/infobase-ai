# i18n parseMissingKeyHandler honours t()'s defaultValue fallback

## Description

S001-F-008 introduced an i18n configuration in `src/i18n/config.ts:32` that overrides i18next's default missing-key behaviour:

```typescript
parseMissingKeyHandler: (key: string) => key,
```

The intent (per F-008's inline comment) was *"developers can spot it without crashing the UI"* — when a translation key is missing from `de.json` / `en.json`, render the raw key string so it stands out during development. But this handler **intercepts** every missing-key lookup, including the standard `t('namespace.key', 'Friendly Fallback')` pattern that already provides a graceful default. With the override in place, `t('formFields.Passnummer', 'Passnummer')` returns `"formFields.Passnummer"` instead of `"Passnummer"`.

Operator-reported leak points (2026-04-30T14:45):

| Where | Call site | Symptom |
|---|---|---|
| Admin → "Create new form field" → form preview | `src/components/workspace/FormViewer.tsx:401`<br>`t(\`formFields.${field.label}\`, field.label)` | Newly-created field shows as `formFields.Passnummer` instead of `Passnummer`. (`formFields` namespace exists but admin-created field labels are not pre-registered.) |
| Document tree → render list (after `Übersetzen` produces a translated render) | `src/components/workspace/CaseTreeExplorer.tsx:61–68, 114, 149, 243, 248, 249, 278` (eight calls)<br>`t('documents.renders.original', 'Original')` etc. | Render labels show as `documents.renders.original`, `documents.renders.translated`, `documents.renders.count` etc. (`documents.renders` namespace doesn't exist in either locale.) |

Both are the same root cause: the handler ignores the `defaultValue` argument that `t()` receives and that i18next would otherwise use as the natural fallback.

The build-time coverage script (`scripts/i18n-coverage.js`, also F-008) catches missing keys in CI — so the runtime handler is redundant for that purpose. The fix is a one-line change to the handler so it respects the call-site's intent.

### Scope discipline

This requirement is **i18n configuration only**. It does not:

- Touch any locale file (`de.json` / `en.json` are unchanged).
- Touch any call site that uses `t()` (the existing `t('foo.bar', 'Friendly Label')` pattern continues to work and now produces the friendly label as intended).
- Add new dependencies (the fix uses i18next's existing `parseMissingKeyHandler` signature, which already accepts the `defaultValue` as its second argument).
- Change the build-time CI check (`scripts/i18n-coverage.js` still surfaces missing keys at build time).

### Out of scope

- **Pre-registering admin-created field labels.** Admins can create arbitrary field labels (e.g. `Passnummer`, `Geburtsort`) at runtime; they cannot be pre-translated. The graceful-fallback path is the right answer.
- **Adding `documents.renders.*` to the locale files.** That's a separate cosmetic improvement; with the fix in place the existing in-call-site fallbacks (`'Original'`, `'Translated'`, `'Anonymized'`, etc.) render correctly, which is enough for sprint 1.
- **Migrating away from `parseMissingKeyHandler` entirely.** Removing the handler would also work (i18next's default is to use defaultValue), but keeping a no-default-value escape hatch is useful — a `t('foo.bar')` call with no fallback still surfaces the raw key, which is a useful loud signal.

## Phases

### Phase 1 — patch the handler

**Goal:** make `parseMissingKeyHandler` return `defaultValue` when one is provided to `t()`, and the raw key otherwise.

**Implementation (single edit to `src/i18n/config.ts`):**

```typescript
// Before:
parseMissingKeyHandler: (key: string) => key,

// After:
parseMissingKeyHandler: (key: string, defaultValue?: string) => defaultValue ?? key,
```

The `defaultValue` parameter is the second argument that i18next forwards from any `t(key, defaultValue)` call site. When `t('foo.bar', 'Friendly Label')` is called and `foo.bar` is missing, i18next now invokes the handler with `defaultValue='Friendly Label'`; the handler returns `'Friendly Label'`. When `t('foo.bar')` is called with no fallback, `defaultValue` is `undefined` and `defaultValue ?? key` falls through to the raw key (existing dev-debug behaviour preserved).

Update the inline comment to reflect the new behaviour:

```typescript
// Returns the call site's defaultValue when provided (so `t('ns.key', 'Friendly Label')`
// renders 'Friendly Label' on a key miss); falls through to the raw key when no
// defaultValue is given (preserves the dev-debug signal for unguarded t() calls).
parseMissingKeyHandler: (key: string, defaultValue?: string) => defaultValue ?? key,
```

**Verification:** TC-01 (source check) + TC-02 (logic unit test) + TC-03 (build sanity).

**Rollback:** revert the line via git.
