## Context

The `/fillForm` command runs an LLM extraction pipeline:

```
chat.py:handle_form_extraction()
  → build_extraction_prompt()          # form_parser.py
  → gemini_service.generate_response() # calls LLM, then runs format_response()
  → parse_extraction_result()          # json.loads() on result
```

When running with small models (e.g. `llama3.2:1b`, `gemma3:27b` at lower precision) in the closed BAMF corporate environment, two failure modes were observed:

### Bug A — `format_response()` destroys valid JSON (latent, all model sizes)

`generate_response()` always applies `format_response()` to the raw LLM output. `format_response()` detects strings that start with `{` and end with `}` as JSON and converts them into markdown tables via `_format_json_as_markdown_table()`. A correctly-formed `{"name": "Ahmad"}` response would arrive at `parse_extraction_result()` as `| Property | Value |\n| --- | --- |...`, causing `json.loads()` to fail. `semantic_search()` already worked around this by calling `self._provider.generate()` directly; form extraction did not.

### Bug B — Small models prepend conversational preamble (small-model behaviour)

Small models often ignore "Return ONLY JSON" instructions at the end of long prompts and open with text like *"I will extract the information and make it in JSON..."*. `parse_extraction_result()` had no fallback to recover the JSON object from within such a response, resulting in `JSONDecodeError: Expecting value: line 1 column 1 (char 0)`.

---

## Requirements

### R1 — Form extraction must bypass `format_response()`
`handle_form_extraction()` MUST call the underlying LLM provider directly (`gemini_service._provider.generate()`), not `generate_response()`. This prevents intermediate formatting from corrupting JSON responses before they reach the parser.

### R2 — Parser MUST recover JSON embedded in preamble text
`parse_extraction_result()` MUST attempt to extract a `{...}` JSON block via regex when the cleaned response does not start with `{` or `[`. This handles models that produce leading/trailing prose around a valid JSON object.

### R3 — Extraction prompt MUST state JSON-only constraint at the top
`build_extraction_prompt()` MUST place the critical JSON-only output instruction as the very first content after the task title — before the field list and document content — so small models with limited attention span receive the constraint at the start of their context window.

### R4 — Lower temperature for extraction calls
Form extraction calls MUST use `temperature=0.3` (vs. the default `0.7` for chat) to reduce model creativity and increase determinism for structured JSON output.

## Implementation

### `backend/api/chat.py` — `handle_form_extraction()`

**Before:**
```python
ai_response = await gemini_service.generate_response(
    prompt=extraction_prompt,
    case_id=case_id,
    document_content=None,
    stream=False
)
```

**After:**
```python
# S001-NFR-007: call the provider directly to bypass format_response(),
# which would convert a valid JSON response into a markdown table.
ai_response = await gemini_service._provider.generate(
    extraction_prompt,
    temperature=0.3,
    top_p=0.8,
    top_k=40,
    max_output_tokens=2048,
)
ai_response = (ai_response or "").strip()
```

### `backend/tools/form_parser.py` — `parse_extraction_result()`

Added regex fallback after code-block stripping:
```python
if not cleaned_response.startswith("{") and not cleaned_response.startswith("["):
    match = re.search(r'\{.*\}', cleaned_response, re.DOTALL)
    if match:
        logger.debug("Extracted JSON block from preamble-laden response")
        cleaned_response = match.group(0)
```

### `backend/tools/form_parser.py` — `build_extraction_prompt()`

Added critical constraint block at the top of the prompt (before field list):
```
CRITICAL INSTRUCTION: Your ENTIRE response must be a single valid JSON object.
Start your response with `{` and end with `}`. Do NOT write any preamble,
explanation, greeting, or commentary — only the JSON object itself.
Example of correct output: {"fullName": "Ahmad Ali", "birthDate": "1990-05-15"}
```

## Generalization beyond `/fillForm`

This requirement was originally scoped to form-fill but expanded to address the same vulnerability in all five LLM-JSON consumer sites. Two refactors generalize the fix:

### Shared utility: `backend/utils/llm_output.py`

Single source of truth for parsing structured LLM output:

- `extract_json_from_llm_response(text, expect, repair_truncation)` — handles code-fence stripping, preamble recovery, optional truncation repair, returns `None` on failure (no exception)
- `JSON_ONLY_HEADER` constant — standardized "respond with ONLY a JSON value" instruction used at the top of every JSON-producing prompt

### Sites refactored to use the utility

| Site | What changed |
|---|---|
| `backend/tools/form_parser.py` | Uses `extract_json_from_llm_response(expect="object")`; prompt header replaced with `JSON_ONLY_HEADER` |
| `backend/services/gemini_service.py::semantic_search` | Uses `extract_json_from_llm_response(expect="array")`; prompt prefixed with `JSON_ONLY_HEADER` |
| `backend/services/validation_service.py` | Uses `extract_json_from_llm_response(repair_truncation=True)`; truncation-balancing logic moved into utility (now reusable) |
| `backend/services/shacl_generator.py::parse_nl_command` | Uses `extract_json_from_llm_response(expect="object")`; prompt prefixed with `JSON_ONLY_HEADER` |
| `backend/services/field_generator.py` | Switched from `generate_response()` to `generate_raw()` (was Bug 2 latent); uses `extract_json_from_llm_response`; `FIELD_GENERATION_PROMPT` prefixed with `JSON_ONLY_HEADER` |

### Effect

- Five consumer sites now share one robust JSON parser. Future tools needing structured output get correctness for free.
- Five prompts now lead with the JSON-only constraint (small models read prompt heads more reliably than tails).
- `field_generator.py` was previously hit by Bug 2 (silent), now uses `generate_raw()`.
- ~80 lines of near-duplicate cleanup logic removed across the codebase.

## What this does NOT cover

- Retry loop (up to 3 attempts) on persistent parse failure — would be S001-NFR-008 if telemetry shows it's needed.
- Structured output / JSON schema enforcement at the LiteLLM layer — requires model and proxy support, out of scope for sprint-001.
- Translation service is not currently in the JSON-output path; if structured translation output is added later, it should use the same utility.
