# End-to-end runnable stack — LiteLLM proxy + backend + frontend on Linux/WSL2

## Description

After all sprint-001 requirements (F-001…F-009, NFR-001…NFR-004, D-001) were polished and implemented, a fresh `docker compose up -d --build` on this Linux/WSL2 host **does not** produce a working application. The individual building blocks are correct, but five integration gaps prevent end-to-end runtime:

1. **Operator-side env files are missing.** `litellm/.env` does not exist (the LiteLLM compose declares `env_file: [.env]` and refuses to start without it), and the root `.env` is effectively empty (57 bytes — only one of the four LLM-related keys is set, neither `LLM_BACKEND` nor `LITELLM_PROXY_URL` is present).
2. **NFR-003 AC #2 is literally violated.** `docker compose -f docker-compose.yml config` emits two warnings: the obsolete `version: "3.9"` field and an `OLLAMA_PID variable is not set` warning caused by un-escaped bash variables (`$!`, `$OLLAMA_PID`) in the ollama service's entrypoint. NFR-003 AC #2 says "validation passes with no warnings about deprecated keys."
3. **The containerised backend cannot reach the LiteLLM proxy on Linux/WSL2.** `litellm/README.md` documents `http://host.docker.internal:4000` as the proxy URL for the umbrella-compose backend, but the umbrella `docker-compose.yml` does **not** add `extra_hosts: ["host.docker.internal:host-gateway"]` to the `backend` service. On Linux/WSL2 (this machine) `host.docker.internal` will not resolve from inside the backend container. Result: every backend → proxy call times out.
4. **Spec drift on `ENABLE_OLLAMA_CONTAINER`.** The `.env.example` documents `ENABLE_OLLAMA_CONTAINER=false` with `Purpose: when true, docker-compose starts the optional local Ollama container.` That is **false** — Compose profiles cannot be activated by env vars in v3.9; the actual mechanism is the `--profile ollama` CLI flag. The var is genuinely a documented intent flag, not a no-op (F-002 ships it intentionally so the operator has a single canonical switch and umbrella scripts can read it), but the wording mis-states the runtime behaviour.
5. **No end-to-end smoke verification has been run.** All sprint-001 verifications were unit/integration tests on individual surfaces. The chain *browser → frontend container → backend container → LiteLLM proxy container → host Ollama → response* has never been exercised.

This requirement closes those five gaps and proves the whole stack runs end-to-end on this Linux/WSL2 host with LiteLLM acting as the LLM front door for a host-local Ollama serving `gemma3:12b`.

### Deployment context — what this requirement is also about

The same image set that comes out of this requirement must deploy to a Kubernetes cluster (BDOP) where **only the LiteLLM proxy URL is provided externally**. Backend, frontend (nginx), and persistent volumes all live inside the cluster; the operator gets a single URL (mapped to the frontend pod's `:3000`). Concrete implications baked into the plan:

- **Single host port for the demo.** All SPA assets, HTTP API, WebSocket chat, and PDFs flow through `:3000`. The frontend container's nginx is the only piece that knows where the backend lives.
- **Single replica for the backend** (operator-confirmed Q4). `backend/api/chat.py:60` declares `active_connections: Dict[str, WebSocket] = {}` — a per-process in-memory dict on the module-level `manager` singleton. With multiple replicas behind a load balancer, a user's WS reconnect could land on a different pod and lose state. Multi-replica chat needs Redis pub/sub or sticky sessions and is **out of scope** for sprint 1.
- **nginx upstream is templated** (`${BACKEND_HOST}:${BACKEND_PORT}`, operator-confirmed Q1) so the same frontend image works under compose service-name DNS (`backend:8000`) and under k8s Service DNS (`backend.<namespace>.svc.cluster.local:8000`).
- **Resource limits** in compose (2 CPU / 2 GB backend, 1 CPU / 1 GB frontend) translate directly to k8s `resources.{requests,limits}`.
- **`litellm/` subproject is dev-only.** In k8s, `LITELLM_PROXY_URL` is set to the BDOP-provided external URL; the local litellm container is not deployed.
- **k8s manifests themselves** (Deployment / Service / Ingress / ConfigMap / PVC) are **out of scope** here — that's a follow-up sprint or BDOP onboarding artifact. This requirement only ensures the images are k8s-ready.

### Topology (the "how things actually connect")

The architecture is **single-origin from the browser's perspective**: everything the browser fetches (`/`, `/api/*`, `/ws/*`) comes from `http://localhost:3000`. The frontend container is an nginx reverse proxy that serves the built SPA and forwards `/api/*` and `/ws/*` to the backend over Docker's internal bridge network using service-name DNS (`backend:8000`). This eliminates hardcoded URLs in the SPA, eliminates CORS configuration, and means any deployment (this WSL2 host, BDOP, k8s, etc.) just needs the nginx `upstream backend` to point at the right place.

```
[Browser]                              ws/http   ──►  http://localhost:3000
                                                            │
                                                            ▼
[Frontend container]                   nginx      ──►  serves SPA (static)
                                                  ──►  /api/* → http://backend:8000/api/*
                                                  ──►  /ws/*  → http://backend:8000/ws/*  (Upgrade headers)
                                                            │
                                                            ▼ Docker service-name DNS, default bridge net
[Backend container]                    FastAPI    ──►  HTTP routers + WS chat handler
                                                  ──►  LLM provider call
                                                            │
                                                            ▼ Authorization: Bearer LITELLM_TOKEN
[via backend extra_hosts → host-gateway]                    host.docker.internal:4000
                                                            │
                                                            ▼
[LiteLLM container]                    proxy      ──►  routes to ollama_chat/<model>
                                                            │
                                                            ▼ Authorization (master key)
[via litellm extra_hosts → host-gateway]                    host.docker.internal:11434
                                                            │
                                                            ▼
[Host daemon]                          ollama     ──►  serves gemma3:12b
```

Three things this diagram makes precise:

1. **Single origin from the browser.** The SPA only ever fetches relative paths (`/api/...`, `/ws/...`) — no `localhost:8000`, no `VITE_API_BASE_URL` baked into the bundle, no CORS configuration. The frontend container's nginx is the only piece of the system that knows where the backend lives, and it knows via Docker service-name DNS. Production deployments swap that one upstream value to repoint the entire stack.
2. **The chat path is WebSocket, proxied through nginx.** `backend/api/chat.py:104` exposes `@router.websocket("/ws/chat/{case_id}")`. The frontend opens `ws://${location.host}/ws/chat/...`, so when the page is loaded from `:3000`, it becomes `ws://localhost:3000/ws/chat/...`. nginx routes that to `backend:8000` with the `Upgrade`/`Connection` headers required for the WS handshake. No `ws://localhost:8000` hardcode anywhere in the SPA.
3. **Two `extra_hosts: ["host.docker.internal:host-gateway"]` mappings are still required.** They live on backend (umbrella compose, added by Phase 3) and litellm (litellm compose, already present). Both are about a *container reaching a host port that lives outside Docker's network* — backend → litellm proxy on `:4000`, litellm → host Ollama on `:11434`. Service-name DNS on the bridge network solves frontend → backend; `extra_hosts` solves the two host-port hops.

### Phase 1.5 — Frontend container as reverse proxy (architectural pivot)

**Goal:** the frontend container becomes the *single origin* the browser talks to. It serves the built SPA and proxies `/api/*` and `/ws/*` to the backend service over Docker's internal bridge network. This eliminates hardcoded URLs in the SPA, eliminates CORS configuration, and means the SPA bundle is deployment-environment-agnostic — the only piece of the system that knows where the backend lives is the frontend container's nginx config.

**Why this phase exists (operator-confirmed pivot):** the previous architecture was "frontend container is static-only; browser talks to backend directly." That works on this WSL2 host because the browser sees `:8000` mapped to the host's localhost, but it requires hardcoded URLs (or `VITE_API_BASE_URL` baked at build time) in the SPA, which breaks the moment the app is deployed to a different origin or reverse-proxied. The user's stated deployment goal makes that deal-breaking. Operator-confirmed in conversation 2026-04-30: switch to nginx-as-reverse-proxy now, before Phase 2 onward.

**Implementation:**

1. **`frontend/nginx.conf.template` (new file — placed at `/etc/nginx/templates/default.conf.template` in the image):**

   The official `nginxinc/nginx-unprivileged` image's default entrypoint runs `envsubst` on every file under `/etc/nginx/templates/*.template` at container start, writing the result to `/etc/nginx/conf.d/`. We rely on that — no custom entrypoint needed. Only `${BACKEND_HOST}` and `${BACKEND_PORT}` are substituted (envsubst skips any `$var` that isn't an env var, so nginx's own `$host`, `$http_upgrade`, etc. pass through unchanged).

   ```nginx
   # WS upgrade map (http-level — included via /etc/nginx/conf.d/*.conf)
   map $http_upgrade $connection_upgrade {
     default upgrade;
     ''      close;
   }

   upstream backend {
     server ${BACKEND_HOST}:${BACKEND_PORT};
     keepalive 16;
   }

   server {
     listen 3000;
     server_name _;
     root /usr/share/nginx/html;
     index index.html;

     # gzip (Q6 — no extra dependencies; nginx ships with gzip module)
     gzip on;
     gzip_vary on;
     gzip_min_length 1024;
     gzip_types text/plain text/css text/xml application/json application/javascript application/xml+rss text/javascript;

     # SPA fallback (Q7-derived: relative URLs, no localhost fallback in bundle)
     location / { try_files $uri $uri/ /index.html; }

     # HTTP API proxy
     location /api/ {
       proxy_pass http://backend;
       proxy_http_version 1.1;
       proxy_set_header Host              $host;
       proxy_set_header X-Real-IP         $remote_addr;
       proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
       proxy_set_header X-Forwarded-Proto $scheme;
       proxy_set_header Connection        "";
       proxy_read_timeout 300s;
     }

     # WebSocket proxy (chat)
     location /ws/ {
       proxy_pass http://backend;
       proxy_http_version 1.1;
       proxy_set_header Upgrade    $http_upgrade;
       proxy_set_header Connection $connection_upgrade;
       proxy_set_header Host       $host;
       proxy_set_header X-Real-IP  $remote_addr;
       proxy_read_timeout 3600s;
       proxy_send_timeout 3600s;
     }

     # Q2: backend serves PDFs via StaticFiles mounts at these paths.
     # Without proxying, the SPA fallback above would swallow them.
     location /root_docs/ {
       proxy_pass http://backend;
       proxy_http_version 1.1;
       proxy_set_header Host              $host;
       proxy_set_header X-Real-IP         $remote_addr;
       proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
       proxy_read_timeout 60s;
     }

     location /documents/ {
       proxy_pass http://backend;
       proxy_http_version 1.1;
       proxy_set_header Host              $host;
       proxy_set_header X-Real-IP         $remote_addr;
       proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
       proxy_read_timeout 60s;
     }
   }
   ```

### Phase 3 — Linux/WSL2 backend ↔ proxy networking + container-correct paths

**Goal:** make `LITELLM_PROXY_URL=http://host.docker.internal:4000` work from inside the backend container on Linux/WSL2 (matching what `litellm/README.md` documents), AND override the two `.env` values that only make sense for the host-run case (`LITELLM_PROXY_URL` and `DOCUMENTS_PATH`) so a fresh `docker compose up -d --build` does the right thing without operator intervention.

**Implementation (edits to `docker-compose.yml` only):**
- In `services.backend`, add:
  ```yaml
  extra_hosts:
    - "host.docker.internal:host-gateway"
  ```
  This mirrors what the LiteLLM compose already does for its container's egress to host Ollama. On macOS/Windows Docker Desktop the directive is a no-op (the resolver already maps it). On Linux/WSL2 it inserts a `/etc/hosts` line at container start pointing at the bridge gateway, which is how Compose surfaces the host.
- Add an `environment:` block to `services.backend` whose entries take precedence over the values pulled from `env_file:`. Two overrides go here, both for the same reason — the env-file value is correct for the host-run case but wrong for the containerised case:
  ```yaml
  # Container-run overrides. The values in env_file (.env) are correct when
  # running the backend with `uvicorn` directly on the host; the substitutions
  # below take precedence under Compose so neither variable has to be edited
  # in .env when switching modes.
  environment:
    LITELLM_PROXY_URL: "http://host.docker.internal:4000"
    DOCUMENTS_PATH: "/var/app/documents"
  ```
  - `LITELLM_PROXY_URL`: from `localhost:4000` (host-run) → `host.docker.internal:4000` (container-run, depends on the `extra_hosts` directive added above).
  - `DOCUMENTS_PATH`: from the `.env.example` default `public/documents` (which would resolve to `/app/public/documents` inside the container — outside the volume mount) → `/var/app/documents` (the actual mount point on `services.backend.volumes` line 17). Without this override, files uploaded with `ENABLE_UPLOAD=true` are written to a non-mounted path and lost on container recreate, contradicting NFR-003 AC #8 ("preserves uploaded files across recreate").

**Verification:**
- TC-S001-NFR-005-06: with the LiteLLM proxy up (Phase 5), the backend container can reach the proxy. The `$LITELLM_TOKEN` expansion happens *inside the container* (via `sh -c '…'`) so the value is read from the container's loaded env, not the host shell:
  ```bash
  docker compose run --rm --no-deps backend sh -c \
    'curl -sf -H "Authorization: Bearer $LITELLM_TOKEN" http://host.docker.internal:4000/health/liveliness'
  ```

### Phase 7 — End-to-end LLM round trip (WebSocket)

**Goal:** a chat message originated *the same way the frontend originates one* — over the WebSocket endpoint `/ws/chat/{case_id}` — produces a model response that demonstrably traversed `client → backend → LiteLLM proxy → host Ollama → gemma3:12b → response back`.

**Why a Python script and not bash:** chat is WebSocket per `backend/api/chat.py:104` (`@router.websocket("/ws/chat/{case_id}")`). The protocol is JSON-over-WS with the message format documented in lines 120–138 of that file. Bash has no native WS client and `wscat` / `websocat` are not installed on this host. The backend's own venv (`backend/venv/bin/python3`) already has `websockets==12.0` per `backend/requirements.txt`, so we reuse it as the test driver.

**Implementation:**
- Create `temp/verify-e2e.py` (executable, shebang `#!/usr/bin/env python3` plus a guard that re-execs under `backend/venv/bin/python3` if the imported `websockets` module is missing). Behaviour:
  1. Read `FRONTEND_PORT` and `BACKEND_PORT` from `.env` (defaults `3000` and `8000`).
  2. Tail `docker compose logs --since 0s -f backend > /tmp/nfr005-backend.log &` (capture PID for cleanup).
  3. **Run two connections** — one through the proxied path (production-realistic), one direct to the backend (sanity check that the backend itself works):
     - Proxied: `ws://localhost:{FRONTEND_PORT}/ws/chat/ACTE-2024-001?language=en` (this is what the SPA opens after Phase 1.5).
     - Direct: `ws://localhost:{BACKEND_PORT}/ws/chat/ACTE-2024-001?language=en` (kept available because `services.backend.ports` is not removed in sprint 1).
  4. For each connection: receive the welcome frame (`{"type":"system",...}`), assert it arrived within 5 s.
  5. Send `{"type":"chat","content":"reply with the single word: pong","caseId":"ACTE-2024-001"}`.
  6. Receive frames until one matches `{"type":"chat_response", "content": "<non-empty>"}` OR `{"type":"error", ...}` (with timeout 60 s — first call may pay the model cold-load cost).
  7. Close the WS cleanly.
  8. Kill the log tailer; grep `/tmp/nfr005-backend.log` for an outbound `litellm` / `host.docker.internal:4000` request line.
  9. Optional: snapshot host Ollama with `curl -s http://localhost:11434/api/ps | jq` to confirm `gemma3:12b` was loaded recently.
  10. Print `OK: e2e chat path traversed (proxied + direct)` on success; non-zero exit + diagnostic on any failure (welcome timeout, error frame, missing log line, missing model snapshot, proxy path failed but direct succeeded → nginx WS config bug).
- Optionally, if Playwright MCP is available, drive the live UI as a third confirmation: open `http://localhost:3000`, find the chat input (selector to be discovered live with `browser_snapshot`), type the same prompt, submit, wait ≤ 60 s for a response bubble. One golden-path check; cost-conscious per the project's Playwright guidance memory.

**Verification:**
- TC-S001-NFR-005-18: `backend/venv/bin/python3 temp/verify-e2e.py` exits `0` within 90 s and stdout contains `OK: e2e chat path traversed`. The chat-response frame must have non-empty `content`. The error-frame branch (`type: error`) is an explicit failure with the error message printed for debug.
