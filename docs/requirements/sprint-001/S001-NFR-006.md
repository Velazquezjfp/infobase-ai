# Path translation for legacy `public/documents/` references after container migration

## Description

S001-NFR-005's container migration moved the document filesystem from `${PROJECT_ROOT}/public/documents/` (the old host-cwd convention) to `${DOCUMENTS_BASE_PATH}` — `/var/app/documents` inside the container by way of the compose `services.backend.environment` override. The runtime side of NFR-005 is correct: the volume mount, the `StaticFiles` mount at `/documents/*`, the LiteLLM proxy hop, the WebSocket chat round-trip — all confirmed end-to-end by NFR-005 Phase 7.

But two artifacts that NFR-005 did not migrate still encode the old prefix:

1. **`backend/data/document_manifest.json`** — every entry's `filePath` is a frozen string of the form `public/documents/ACTE-2024-001/<folder>/<file>` (the project-root-relative path).
2. **`src/components/workspace/DocumentViewer.tsx:213`** — when a document is selected, the SPA constructs the same `public/documents/<case>/<folder>/<file>` path and POSTs it to `/api/documents/extract-pdf-text`.

Three places consume these literal strings as filesystem paths and break inside the container:

- `backend/services/pdf_service.py::extract_text(pdf_path)` — `path = Path(pdf_path)` resolves against cwd `/app`, so `public/documents/...` becomes `/app/public/documents/...` (which does not exist in the container).
- `backend/services/pdf_service.py::extract_text_with_positions(pdf_path)` and `get_page_count(pdf_path)` — same pattern.
- `backend/services/email_service.py::parse_eml_file(file_path)` — same pattern.

Result: `POST /api/documents/extract-pdf-text` returns `404 PDF file not found` for every legacy-shaped path. Without extracted text, `selectedDocument.content` stays empty in the SPA; the WebSocket `documentContent` field is empty in every chat payload; `handle_form_extraction` runs against an empty document and (correctly, given empty input) produces zero suggested fields. The user-visible symptom is **"Ich habe 0 Felder aus dem Dokument extrahiert"** when clicking `Formular ausfüllen` against a real PDF — and the inability to chat in document context.

The chat WebSocket protocol, the `gemini_service` prompt assembly, the LiteLLM provider call, and every other piece of the chain documented in [`docs-v1/diagrams/context-management-flow.mmd`](../../docs-v1/diagrams/context-management-flow.mmd) are correctly wired. **The fix is purely path semantics.** It needs to happen at exactly one boundary and leave every other surface untouched.

### Why a translation helper rather than a manifest migration

Two equivalent fixes were considered:

- **Option A** (chosen) — a small `resolve_document_path()` helper in `backend/config.py` that maps legacy `public/documents/<rest>` → `${DOCUMENTS_BASE_PATH}/<rest>` and passes everything else through. Used at the three service-layer entry points where Python opens the file.
- **Option B** — rewrite every `filePath` in `document_manifest.json` to use the absolute container path.

Option A is preferred because:

1. The helper is one function, ~10 lines, fully testable in isolation, and unaffects host-dev (`DOCUMENTS_BASE_PATH=public/documents` makes the translation a no-op).
2. It avoids touching application data (`document_manifest.json`) — no migration script, no rollback story.
3. Both legacy and absolute path forms continue to work — useful for any code that produces absolute paths today.
4. The frontend stays unchanged. The legacy-shaped path it sends today continues to work; future cleanup can canonicalize at leisure.

Operator-confirmed during diagnosis (2026-04-30T13:25): "yes don't touch the manifest and let this deployable version translate it."

### Scope discipline

This requirement is **plumbing only**. It does not:

- Add new endpoints, new methods that change behaviour, or new prompt-building logic.
- Change the WebSocket protocol or any frontend payload field.
- Modify `gemini_service`, `chat.py`, `documents.py` (the API handlers stay as they are; only the service-layer path resolution changes).
- Vendor the PDF.js worker (a separate concern; PDF *visual rendering* in the browser fails because `unpkg.com/pdfjs-dist@5.4.296/build/pdf.worker.min.mjs` is CORS-blocked, but server-side text extraction — what feeds the LLM — does not depend on the worker).

### Out of scope (deferred to follow-ups)

- **PDF.js worker vendoring** — needed for in-browser PDF rendering and for closed-environment deployment. The form-fill chain works without it; tracked separately.
- **Manifest canonicalization** — making `filePath` use absolute container paths. The translation helper makes this unnecessary.
- **Frontend path canonicalization** — having `DocumentViewer.tsx` produce already-resolved paths. Same reason.

## Phases (live — polish in place after each)

### Phase 1 — `resolve_document_path` helper in `backend/config.py`

**Goal:** add a single small helper that translates legacy `public/documents/<rest>` paths to `${DOCUMENTS_BASE_PATH}/<rest>` and passes everything else through.

**Implementation:**

Add to `backend/config.py`, immediately after the `DOCUMENTS_BASE_PATH` definition:

```python
from pathlib import Path

LEGACY_DOCUMENTS_PREFIX = "public/documents/"


def resolve_document_path(path: str) -> Path:
    """
    Resolve a document path to its on-disk location, translating the legacy
    project-root-relative prefix (`public/documents/<rest>`) to the configured
    DOCUMENTS_BASE_PATH (`/var/app/documents/<rest>` in the containerised
    deployment, `public/documents/<rest>` in host-dev — same string, no-op).

    The translation is needed because:
      - `document_manifest.json` and the SPA's DocumentViewer encode the legacy
        prefix as a frozen string from the host-dev era.
      - Inside the container, cwd is `/app` and `public/documents/` does not
        exist — files live at DOCUMENTS_BASE_PATH instead.

    Absolute paths (anything starting with `/`) and other relative paths are
    passed through unchanged. Tests cover both forms.

    Args:
        path: Legacy or already-resolved path, as a string.

    Returns:
        A `pathlib.Path` pointing at the on-disk file.
    """
    if path.startswith(LEGACY_DOCUMENTS_PREFIX):
        # Strip the legacy prefix and re-anchor under DOCUMENTS_BASE_PATH.
        # Note: when DOCUMENTS_BASE_PATH itself is `public/documents` (host-dev),
        # this is a no-op (the resulting path is the same string).
        relative = path[len(LEGACY_DOCUMENTS_PREFIX):]
        return Path(DOCUMENTS_BASE_PATH) / relative
    return Path(path)
```

**Verification:**

- TC-S001-NFR-006-01 covers the helper directly:
  - Container scenario (`DOCUMENTS_BASE_PATH=/var/app/documents`):
    - `resolve_document_path("public/documents/x.pdf")` → `Path("/var/app/documents/x.pdf")`
    - `resolve_document_path("/var/app/documents/x.pdf")` → `Path("/var/app/documents/x.pdf")` (unchanged)
  - Host-dev scenario (`DOCUMENTS_BASE_PATH=public/documents`):
    - `resolve_document_path("public/documents/x.pdf")` → `Path("public/documents/x.pdf")` (no-op — same string)
  - Edge: `resolve_document_path("root_docs/x.pdf")` → `Path("root_docs/x.pdf")` (unchanged — non-legacy relative path passes through).

**Rollback:** delete the helper + import via git.

### 2026-04-30T15:30:00Z — Polish addendum #3: hardcoded `Path("public") / "documents"` literals on the upload-write side (operator-reported)

After the demo came up via SSH tunnel from the operator's laptop, the backend logs showed repeated `FileNotFoundError: '/app/public/documents/ACTE-2024-001/personal-data'` followed by `PermissionError: '/app/public'`. Diagnosis: four production-code sites construct write paths from scratch with `Path("public") / "documents"` rather than reading them from the manifest. The previous NFR-006 polish addressed the *read* side (paths flowing in from the manifest / SPA via `extract-pdf-text`, `parse-email`, `translate`, etc.) — the helper translated those before the file open. But these four sites build paths during the upload-write workflow and never went through `resolve_document_path()`:

| File | Site | What it does |
|---|---|---|
| `backend/services/file_service.py:303` | `delete_file()` constructs `base_dir / case_id / folder_id / safe_filename` to delete | hardcoded literal → wrong location in container |
| `backend/services/file_service.py:420` | `file_exists()` checks if a case file is on disk | same literal → always returns False inside container |
| `backend/api/files.py:162` | `/api/files/upload` POST builds the target write path; calls `create_folder_if_needed()` which `mkdir(parents=True)` walks up to `/app/public` (root-owned) → `PermissionError` | the source of the operator-visible traceback |

### 2026-04-30T15:50:00Z — Polish addendum #4: `backend/api/folders.py` had its OWN hardcoded path

After demo bring-up via SSH tunnel, operator reported "folders are not visible in admin mode" and "Add field functionality doesn't load." Traceback in backend logs:

```
File "/app/backend/api/folders.py", line 218, in get_folders
File "/app/backend/api/folders.py", line 191, in ensure_folder_directory
PermissionError: [Errno 13] Permission denied: '/app/public'
```

Root cause: `backend/api/folders.py:34` had its own hardcoded path constructed via `__file__`-walking rather than the `Path("public") / "documents"` literal:

```python
DOCUMENTS_DIR = Path(__file__).parent.parent.parent / "public" / "documents"
```

Inside the container, `__file__` is `/app/backend/api/folders.py`, so:
- `__file__.parent.parent.parent` = `/app`
- `/app / "public" / "documents"` = `/app/public/documents`

When `GET /api/folders/<case_id>` calls `ensure_folder_directory()`, that does `mkdir(parents=True, exist_ok=True)` on a subpath of `DOCUMENTS_DIR`. With parents=True it walks up trying to create `/app/public/documents/<case>/<folder>` → `/app/public/documents/<case>` → `/app/public/documents` → `/app/public`, the last of which exists but is root-owned (image was built as root before the `USER app` switch, so `/app` and its children that weren't explicitly chowned are root). PermissionError. Endpoint returns 500. The SPA's admin module relies on the folder list to populate the form-builder's field-selector, document-type filters, etc. — without the folder list, the admin UI renders an empty/broken state.

The previous sweep grepped for `Path("public")` literals only and missed the `__file__`-walked variant. Updated grep pattern to catch both shapes:

```bash
grep -rnE "Path\(__file__\)\..*[\"']public[\"']|Path\([\"']public[\"']\)" backend/
```

After this edit and before, the result of the new pattern was a single-line fix.

Edits:
- `backend/api/folders.py`: added `from backend import config` import; replaced the `Path(__file__).parent.parent.parent / "public" / "documents"` line with `Path(config.DOCUMENTS_BASE_PATH)`. Comment block above the line documents the historical issue and points at NFR-006.

After rebuild + restart, both the folders panel in user mode and the admin module's form-builder render correctly. The form-field generation API (`POST /api/admin/generate-field`) was always working — it returned 200 with a generated field even before — but the surrounding admin UI couldn't display it because the folder-list query was 500-ing.
